Source-confirmed repairs in V45.3.10
1. Failed desktop comment-detail opens can no longer leave a permanent polling loop.
   V45.3.9 intentionally kept commentOpen alive without a miss limit whenever a Feed comment click had promoted the current post to a desktop /video or /photo route. If TikTok never mounted the real comment DOM because of a failed request, login gate, changed markup or blocked sheet, commentOpen could remain true forever and the singleton 450 ms presence check could keep rescheduling indefinitely. V45.3.10 keeps the short normal miss limit (8) and gives a desktop detail-route comment a much longer but finite 36-miss grace window (~16.2 s). If no real sheet appears, state and polling are released and the shell is restored.

2. Top-level mobile destinations no longer get an extra floating native Back button.
   The old secondaryBack rule included every mobileSecondary route. Because Shop, Inbox, the user's own Profile and Discover/Community are top-level destinations with native bottom navigation, they could receive an unnecessary floating Back overlay in addition to their real page controls. V45.3.10 suppresses that wrapper Back control for those top-level destinations while retaining Back for Search, upload/detail pages, external creator profiles and other nested mobile routes; LIVE keeps its close control.

3. Own-profile identity now survives own Profile -> another creator -> Back.
   V45.3.9 correctly stopped post/photo links from being misclassified as external profiles, but visiting a genuinely different bare /@creator profile still cleared ownProfileRoute with no way to recognize the user's own profile when WebView history returned to it. V45.3.10 records the canonical bare profile path when the native Profile tab resolves, preserves that identity while visiting another creator, and restores ownProfileRoute when history comes back to the recorded path.

4. Profile-path comparison is canonicalized.
   TikTok can represent the same bare profile as /@user or /@user/. V45.3.10 lowercases through the existing URL path parser and removes one trailing slash before storing/comparing the own-profile path, so an otherwise identical history return is not treated as an external profile merely because of slash form.

5. Java and JavaScript now use the same narrow definition of a profile route.
   The Java classifier previously accepted any /@... descendant except /video and /photo, while the bridge already limited ownership changes to a bare /@user path. V45.3.10 tightens Java to the same bare-profile contract. /@user/live and other descendants are no longer profile routes by accident.

6. Clicking a link to the profile already being viewed no longer clears ownership.
   The bridge now compares the clicked bare profile path with location.pathname (ignoring one trailing slash). A self-link on the current profile does not call externalProfileOpened(); a genuinely different creator still does.

7. External-profile ownership is published before default anchor navigation.
   JavascriptInterface callbacks can race the anchor's default navigation. V45.3.10 publishes ownProfileRoute=false / externalProfileRoute=true immediately in the bridge callback (the same intent-first principle already used by commentOpen), then posts only the visual shell work to the UI thread. The flags are volatile so shouldOverrideUrlLoading/updateShellForUrl cannot capture the new creator path as the user's own profile during that race.

8. Own-profile identity survives Activity/process recreation.
   own_profile_path is saved alongside own_profile and restored with WebView state. Feed recreation rules remain unchanged; no serialized Feed DOM is restored.
